# 外部参考调研（2026-10-31）

调研范围：用 Claude、Claude Code 或其他编程 Agent 做视频的 skill、开源工具、文章与社区分享，重点看产品演示片。网页部分用网页搜索加逐个打开仓库首页；X 社区部分用 grok 检索，见第五节。

各项目的细节多数来自它们自己的 README，没有逐个装起来验证。星标、安装量这类数字来自聚合站，不可靠，下文不引用。

## 一、结论

1. **没有找到对口的路演片 skill。** 现有项目分两类：
   - **短宣传片**：20 到 60 秒的产品发布片、落地页循环，多数基于 Remotion，界面是截图或重建的组件。
   - **录屏演示**：Agent 操作真实应用，加光标、缩放、配音、字幕，多为英文教程或产品演示，片长几分钟以内。

   这两类都没有覆盖我们的场景：十到三十分钟的分段长片，配合讲者现场使用，带中文政务或企业口径，用国内配音服务，配乐现场作曲并卡点。
2. **我们的几项核心做法，社区已经各自验证过，方向是对的。**
   - 以旁白为骨架：Kiln 团队原话是“Audio leads, video follows”，先画面后配音的那一版被迫整片重剪。
   - 逐帧确定性渲染：Remotion、HyperFrames、product-film 都是“画面是时间的纯函数”；screenwright 和 videowright 用受控的虚拟时钟。
   - 入口文件精简、细节放 references：saas-product-demo-video 的做法和我们一样。
   - 坑与兜底清单：同一个项目整理了 80 条编号的坑，每条写症状、原因、修法。
3. **我们的差异化在这几处：**
   - 在 iframe 里真实操作产品，并逐帧锁住虚拟时钟。
   - 长片分段，配合讲者，出串场稿。
   - 客户背调与文风分档。
   - 中文配音服务实测与推荐。
   - 按时间轴现场作曲卡点。
   - 两机分段渲染。
4. **可以直接借的东西**见第三节，结合 X 社区结果重排的优先级见第六节。

## 三、可借鉴的做法

### 流程与交互
- **缺省就给默认，并说明选了什么**（saas-product-demo-video）。和我们的“全部按推荐”一致，可以在每轮结束时补一句“没答的这几项我按推荐处理了”。
- **先给风格帧再动手**（product-film）。我们的试片审核点之前，可以先给两三张关键帧，确认片头、章节卡、字幕样式，比试片更早、更便宜。
- **两段式门槛**（vorec）。花钱或花时间的事放在用户确认之后：付费配音、全片渲染之前各确认一次。我们的审核点 1、2 已经覆盖，全片渲染前可以再报一次预计耗时。
- **新鲜的眼睛**（product-launch-video）。Agent 自己看久了会看不出问题。审核点之前，可以让另一个子任务以观众视角复查：设计、可读性、节奏、口径。

### 真实界面与分镜起草
- **从页面起草段落表**（aidemo 的 `init --from-url`）。体检时顺带遍历产品的菜单和主要页面，给出段落表初稿。
- **从测试起草时间轴**（screenwright）。用户的产品有端到端测试时，直接从测试里取操作序列和选择器。
- **不伪造结果**（ai-product-demo-video）。我们的回放缓存来自真实调用，要在 SKILL.md 里写明“缓存必须来自真实接口调用，不手写结果”。

### 时间对齐
- **词级强制对齐**（explainroo、videowright）。我们现在按字数比例估锚点，误差在长句里会变大。改成合成后用强制对齐模型拿到每个字的时刻（本机 mlx-audio 已带 Qwen3 强制对齐模块），锚点就准了。
- **旁白长于动作时停帧**（aidemo、ai-product-demo-video）。不要拉慢动作。我们的镜头会缓推，停帧时画面不会死。

### 镜头
- **镜头规则补三条**（explainroo）：
  - 标注停留期间镜头不切掉标注。
  - 段尾拉回全景，让最后一帧看得到全貌。
  - 时间不够就不推近。
- **弹簧镜头作为可选风格**（Screen Studio 一类）。我们的镜头是脚本写死的，控制精确；可以加一个弹簧平滑选项，让推拉更有惯性。

### 配乐与音效
- **测量音效起音**（saas-product-demo-video）。很多音效文件开头有一段空白，不测会晚半拍。每个音效文件测一次起音偏移，存进音效库清单。
- **按配乐调性做提示音**（code-video-skill）。提示音、上扬音按当段配乐的调性生成，听感更融。
- **用户自带配乐时检测节拍是否可靠**（saas-product-demo-video）。拍点不稳的曲子先告诉用户，再决定卡点方式。

### 检查
借过来加进 `scripts/qa`：
- **远看可读性**：按投影或会场后排的视距估算最小字号。对应 explainroo 的手机宽度检查。
- **镜头急动**：相邻帧镜头加速度过大就报。
- **打字预算**：打字时长超过画面时长就报。
- **文字裁切与重叠**：查字幕、标注、章节卡的文字有没有被截断或互相压住。
- **成片解码检查**：时长、帧率、音轨、首尾帧。

### 交付
- **导出剪映草稿**（video-shotcraft）。讲者常想自己改一个字、挪一个转场，剪映草稿对国内用户最友好。
- **附带物**：封面图、带章节的字幕、纯文本旁白、录制报告。

### 工程
- **会话交接文件**（saas-product-demo-video、claude-code-video-toolkit）。长片要做好几个会话，`roadshow/进度.json` 记录做到哪一步、哪些文件已生成，新会话先读它，对照实际文件核对。
- **失败保留诊断**（aidemo）。渲染失败时保留已渲的分块、截图和日志，不要从头来。
- **文档与代码不脱节**（aidemo、vorec）。引擎的编排函数清单由代码生成，`运镜与编排.md` 引用它；仓库自检脚本检查文档里提到的命令和文件是否存在。

## 五、X 社区（grok 检索）

grok 在 X 上收录了 28 条帖子与线程，时间集中在 2026 年 10 月下旬，说明这个方向最近非常热。X 的帖子没有逐条打开核对；报告里点名的 9 个 GitHub 仓库都用 GitHub 接口核对过，全部真实存在。

### 最接近我们的案例
- **[王树义（@wshuyi）](https://x.com/wshuyi/status/2116328521195032701)**：一条操作演示片，由 Claude Code 全程规划、操作真实界面、录制、剪辑、配音。中文圈里和我们最像的做法。
- **[ccomkhj/product-demo](https://github.com/ccomkhj/product-demo)**（Apache-2.0）：
  - 一句话描述功能，缺什么先问，写出脚本等用户确认后才录。
  - 在真实 Chrome 里点击，本地 Kokoro 配音，每次点击落在念到它的那个词上。
  - 剪掉空等时间，烧字幕。
  - 后期另起一条命令处理，原片不动。
- **[Josh Pigford（@Shpigford）](https://x.com/Shpigford/status/2015250030815584647)**：用产品仓库里现成的 React 组件还原界面，先写分镜与时长，再分段生成旁白、配乐、点击与打字音效，两三个小时出片。他发现 TTS 没法按场景时长一次念完，只能按场景切成多段再对齐。

### 方法论
- **[超级峰的视频设计方法论](https://github.com/mileson/chaojifeng-video-design)**（MIT，中文）：
  - 主线从“观众要得到的变化”出发；产品演示的主线是“真实任务、关键操作、结果证据”。
  - 声画分三层：段落改空间尺度，乐句推动作与视线，瞬间让切镜和强调落在重音上。
  - 验收分层且互不替代：前三秒看主体与任务是否清楚；正常速度读完字幕；连续回放听声画；最后才是脚本检查。
  - 没实际看过、听过的项目标“未验证”，不拿脚本检查冒充审片。
  - 局部修改后只复验受影响的部分。
- **[vandit（@v4nd1t）](https://x.com/v4nd1t/status/2116127618437087466)**：
  - 渲染容易，品味难。他把缓动、组件、成片配方写成 Agent 可读的文件，认为“给模型的文件比换哪个模型更重要”。
  - 同一个会话既做片又打分会放水：36 次里有 18 次空过检查。要用全尺寸静帧加新会话来评。
- **[Kiln 的发布片](https://kiln.tech/blog/we_made_our_launch_video_in_claude_code)**：先定音频再排画面（见第二节）。

## 六、据此调整后的建议（按优先级）

1. **词级强制对齐替代字数估算**，锚点精度直接提升。社区的主流做法都是逐字时间戳。
2. **运镜禁令写进规范**：不连续推镜，推近之后必须停留，每次操作最多推一次。
3. **复查交给新会话或子任务**：审核点 1、2 之前，用全尺寸静帧加观众视角复查设计、可读性、节奏、口径；做片的会话不给自己打分。
4. **验收分层，没看过的标“未验证”**：交付报告分三栏写明机器检查过的、Agent 看过的、只有用户能判断的。
5. **风格帧**：审核点 1 和 2 之间，给片头、章节卡、字幕样式各一张。
6. **渲染器核对两项**：色彩范围转换、截帧格式与质量。
7. **`scripts/qa` 补四项**：远看可读性、镜头急动、打字预算、文字裁切重叠。
8. **会话交接文件** `roadshow/进度.json`；局部修改后只复验受影响的段。
9. **体检时从页面起草段落表**；有端到端测试时从测试起草。
10. **导出剪映草稿**作为可选交付物。
11. **音效起音测量**进音效库清单。
12. **产品演示主线补一种写法**：“真实任务、关键操作、结果证据”，作为“一个角色的一天”的骨架。
13. **用户给参考片时**，抽帧分析切点与缩放时机，写进风格档案。
14. **SKILL.md 写明回放缓存必须来自真实调用。**
